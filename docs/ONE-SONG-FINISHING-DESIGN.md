# 완성본 한 곡: 지금 하는 보정과 남은 설계

목표는 여러 결과를 보여 주고 고르게 하는 것이 아니라 버튼 한 번으로 완성도 있는 한 곡을 받는 것이다. 이 문서는
그 목표에 대해 지금 무엇이 되어 있고, 남은 후보 가운데 무엇을 어떤 근거가 생기면 만들지를 적는다. 동작의 세부는
[자동 품질 검사](AUTO-QUALITY.md)에 있다.

## 보정은 세 가지다

| 종류 | 뜻 | 지금 |
| --- | --- | --- |
| 다시 뽑기 | 새 seed로 전곡을 다시 만든다. **다른 곡**을 얻는 탐색이다 | 전체 무음·클리핑·큰 길이 차이·크게 틀린 가사·통째로 빠진 후렴이나 긴 구절이 측정되면 최대 3회 |
| 같은 곡의 한 부분 다시 만들기 | 고른 곡은 그대로 두고 한 구간만 새로 만든다 | 사용자가 고른 구간을 원곡 샘플 보존·실제 템포로 이어 붙인다. 부르지 않은 가사 줄을 자동으로 다시 만드는 단계는 있지만 기본으로 꺼져 있다 |
| 소리를 직접 고치기 | 이미 있는 파형을 신호 처리로 바꾼다 | DC 제거, peak·true peak에 맞춘 선형 감쇄, 5 ms 경계 fade, 수정 구간에서 원곡 peak를 넘는 꼭대기만 낮추기 |

세 가지 모두 **검출 → 처리 → 같은 검사로 다시 확인 → 나빠졌으면 원래 것 유지**의 순서를 따른다. 검출이 믿을 만하지
않은 결함에는 처리를 붙이지 않는다. 처리 뒤에 다시 잴 수 없는 것(더 듣기 좋아졌는가)은 자동으로 채택하지 않는다.

## 측정이 말해 주지 않는 것

완성도에는 깨지지 않은 소리, 설득력 있는 전개·종결, 취향이 따로 있다. 지금의 검사와 보정은 첫째와, 둘째 가운데
"쓴 가사를 다 불렀는가"만 다룬다. 네 테이크 실측에서 사용자가 고른 것은 가사 일치가 가장 낮고 두 줄을 부르지 않은
테이크였다. 그래서 다음을 지킨다.

- 측정으로 시도들을 정렬은 하되, 그 순서가 사람의 선택을 예측한다고 말하지 않는다.
- 자동으로 고친 결과는 고치기 전 것을 지우지 않고, 화면에서 바로 번갈아 들을 수 있게 둔다.
- 측정으로 "고쳐졌다"는 것과 듣기에 나아졌다는 것은 다르다. 가사 누락 수리는 두 곡 모두에서 빠진 줄을 불리게
  했지만, 사용자는 한 곡은 새 선율이 곡과 어울리지 않는다며 보정 전을 골랐고 다른 곡은 비슷하다고 했다.
- 무엇을 다음에 만들지는 결함의 심각성이 아니라 **사용자가 실제로 싫다고 한 것**에서 정한다. 지금까지 귀로 확인된
  불만은 반주가 비는 것, 늘어지는 전주, 조 밖의 음, 옛 가요 같은 소리이며, 믹스에서 보컬이 묻힌다는 불만은 없었다.

## 엔진에서 확인한 사실

고정한 ACE-Step v0.1.8 / XL turbo / native MLX에서 코드를 읽고 실제 출력으로 확인한 것이다.

- 구간 수정은 원곡 파형을 구간 밖에 도로 붙인 뒤 전곡을 −1 dBFS로 다시 맞춘다(`inference.py`의 normalization).
  디코딩 결과의 peak가 1을 넘으면 그 전에 한 번 더 나눈다(`generate_music_decode.py`). 그래서 엔진 결과는 구간
  밖이 원곡 × gain이고, 저장된 12건에서 gain은 −0.79 ~ −1.00 dB, 되돌린 뒤의 차이는 −73 ~ −78 dB였다.
- 파형 연결 폭은 강도에 묶여 최대 50 ms다(`_resolve_repaint_config`). REST가 받는 crossfade 값은 쓰이지 않는다.
- 새로 만든 구간은 원곡 전체의 peak보다 0.8–1.0 dB 높은 꼭대기를 갖는 일이 흔했지만, RMS는 바꾼 구간보다
  크지 않았다(−3.6 ~ +0.4 dB, 내용이 달라진 한 건 +3.2 dB).
- Turbo는 8 step으로 제한되고 CFG는 1로 고정된다. 숫자를 올리는 설정은 효과가 없다.
- REST 결과는 음원 경로와 메타만 돌려준다. 생성 코드·latent는 받지 못한다.
- 같은 요청·seed는 같은 곡을 다시 만든다(3분 곡에서 같은 가사 누락과 같은 일치 단위 수).
- 곡이 요청한 BPM대로 연주된다는 보장이 없다(84 요청 → 87.6, 98 요청 → 88.4, 125 요청 → 126.0). 구간 수정은
  요청 BPM을 강하게 따르므로, 원곡과 다르면 끝 이음매에서 박이 어긋난다. 그래서 수정은 원곡에서 잰 템포로
  요청한다. BPM은 정수만 받는다.
- 원곡 길이를 넘는 범위의 수정(끝 연장) 경로가 엔진에 있지만 앱은 길이를 넘는 범위를 받지 않는다. 길이가 달라지는
  결과에는 원곡 보존 이어 붙이기를 적용할 수 없다.

## 남은 후보

위에서부터 근거가 가깝다. "만들기 전에"가 채워지지 않은 것은 만들지 않는다.

| 후보 | 지금 아는 것 | 만들기 전에 |
| --- | --- | --- |
| 가사 누락 수리를 다시 켜기 | 영어 두 곡에서 빠진 줄은 불렸지만 한 곡은 새 선율이 어울리지 않아 사용자가 보정 전을 골랐다 | 새로 부른 선율이 곡에 맞는지 가릴 근거(예: 같은 가사의 다른 반복과 선율 비교). 그 전에는 줄과 구간만 보여 준다 |
| 이음매의 박 어긋남을 확인할 것으로 | 박자가 깨진다고 들은 이음매는 68–125 ms, 깨지지 않는다고 들은 이음매(템포 맞춘 것 포함)는 1–25 ms였다 | 템포를 맞춘 뒤에도 어긋남이 큰 수정이 얼마나 자주 나오는지 세기 |
| 원곡 자체의 박자 깨짐 | 사용자가 짚은 42초 지점을 지금 박자 검사는 놓쳤다. 8박 창 템포 추정은 그 근처에서 튀었다 | 같은 유형이 다른 곡에서도 귀로 확인될 것 |
| 끝이 잘린 곡 판정과 끝 연장 | 끝 5 ms fade는 잘린 끝을 고치지 않는다. 기본 규칙 요청에 `[Outro]`가 다시 붙게 된 뒤의 발생률은 모른다 | 새로 만든 곡에서 끝이 잘렸다고 사용자가 짚은 사례. 그 사례를 가려내는 측정(끝 0.75초의 보컬 활동, 끝 에너지) |
| 반주가 비는 구간 | 사용자의 가장 일관된 불만. 네 테이크 모두 bridge에서 kick·bass가 빠졌고 문구를 바꿔도 줄지 않았다. 반주 끊김 진단은 한 곡에서 0.25초짜리 의심을 14번 냈고 맞는지 모른다 | 사용자가 "여기가 빈다"고 짚은 구간 몇 개. 그 구간을 가려내는 측정이 정해지면 가사 수리와 같은 틀로 그 구간만 다시 만들기 |
| 측정으로 테이크 고르기 | 지금의 값(가사 일치·kick·bass 빠짐·전주 길이)은 한 번의 청취 선택을 맞히지 못했다 | 사용자가 들은 테이크의 좋다/싫다 기록이 더 쌓일 것. 그 전에는 여러 테이크를 만들어 고르는 기능을 넣지 않는다 |
| 보컬·반주 다시 섞기(UMXHQ) | 보컬 추정을 원 믹스에 더하거나 빼는 방식은 가능하다. 분리 누출이 함께 커진다. 보컬이 묻힌다는 불만은 없었다 | 그 불만이 실제로 나오고, 한 곡에서 원본과 처리본을 귀로 비교해 확인될 것 |
| 박자 time-warp, 보컬 음정 보정 | 박자 검사의 통제 변형 검출률이 21–46%다. 손으로 건드린 사본은 더 나빴다 | 만들지 않는다. 박자 문제는 그 구간을 다시 만드는 쪽이 원곡을 덜 해친다 |
| 음악 복원 모델(SonicMaster 등) | 공개 구현이 Python 3.13을 요구하고, 이 프로젝트의 3.12·Apple Silicon에서 돌려 본 적이 없다. 가사·구성·선율은 고치지 못한다 | 음질 자체(금속성·대역 손실)에 대한 사용자 불만. 지금은 없다 |
| 드럼·베이스·코드 뼈대를 먼저 만들고 그 위에 생성 | 반주 지속을 프롬프트가 아니라 조건으로 주는 방법. MLX의 cover는 조건을 적용하는 step 수로만 강도를 조절한다(8 step) | 반주가 비는 구간을 구간 수정으로 고칠 수 없다고 확인된 뒤의 실험 |

## 새 보정을 넣을 때의 조건

1. 대상 결함을 실제 생성 곡에서 가려내는 측정이 있고, 그 측정이 정상 곡에서 얼마나 자주 울리는지 저장된 곡으로
   세어 본다.
2. 처리 뒤 같은 측정으로 다시 확인하고, 바꾸지 않겠다고 한 부분이 바뀌지 않았는지 파형으로 확인한다.
3. 실패하거나 다른 검사가 나빠지면 고치기 전 것을 그대로 건넨다. 버린 시도와 이유를 남긴다.
4. 실제 추론으로 처음부터 끝까지 한 번 이상 돌리고, 사용자가 들을 고치기 전·후를 `exports/`에 둔다.
5. 예산(시도 횟수)을 batch에 고정하고, 끄는 방법을 둔다.

## 2026-10-05 Music 3 음악성 개선과 기준 곡 비교

사용자는 Music 3 한국어 후보를 듣고 이전보다 음악 수준이 낮아졌다고 평가했다. 이 의견은
해당 후보의 사람 청취 기록에 남겼다. 높은 가사 인식률은 음악성을 승인하는 근거가 아니다.
이번 요청의 최소 기준은 사용자가 좋다고 평가한 `en-202610071-enhanced-eight.wav`이며,
기준 원본·과거 이력은 그대로 둔다. 커밋은 핵심 생성·실행, 앱, 검증 도구·문서로 나눈다.

- caption v3: 기존 여섯 기본 규칙은 유지하고 장르별 선율·감정·구절/후렴 대비를 프리셋에
  추가했다. `melodic-hook`, `expressive-performance`는 선택형 추가 규칙이다. 현재 프리셋과
  규칙의 Music 3용 문장은 새 요청에 동결되며, 이전 snapshot은 당시 문장으로 유지한다.
  사용자 청취 피드백에 따라 선율 규칙은 도입의 주제가 후렴에서 돌아오고, 짧은 리듬·선율
  동기와 하강 응답 구절이 반복되도록 보완했다. 2줄·4줄 후렴과 연주곡을 구분하며, 가사와
  과거 snapshot을 유지한다. 이 마지막 안내의 실제 청취 개선은 아직 확인하지 않았다.
- 수치 시간표를 모델 caption에서 제거하고 실제 가사 구간의 음악적 역할을 안내한다.
  추정 시간·마디·음절 수는 `songPlan`과 미리보기에 보존한다. 아래 v2 시간표 실험은 과거
  관찰이며 현재 방식의 개선 증거로 삼지 않는다.
- 같은 프로젝트의 독립 후보도 같은 위치에서 A/B 재생할 수 있다. 빠른 전환의 위치 초기화와
  짧은 비교곡의 구간 반복 오류를 수정했다. 재생 비교는 추천·최종 선택·사람 평가를 바꾸지 않는다.
  `listened`는 ‘들어 봤어요’로 표시하며 취향 판정을 대신하지 않는다.
- 실런타임은 필수 tokenizer와 caption/lyrics special-token ID, 모델 구조·음원 설정·MXFP8
  계약을 확인한다. upstream의 합성 tokenizer fallback으로 정상 음악인 것처럼 생성하지 않는다.
- 공식 Diffusers와 pinned MLX 구현의 수식 대조에서 오류를 찾지 못했다. 작은 무작위 모델의
  48 frames × 3 seeds × F32/BF16 검사에서는 eager/lazy 결과가 모두 bitwise 동일했다.
  실제 대형 체크포인트의 전체 동일성을 증명한 검사는 아니다. 감사 기록은
  `.runtime/music3-quality-audit/`에 보존한다.
- 새 `scripts/compare_music3_quality.py`는 기준 후보를 크기·SHA-256까지 확인해 재생용으로
  명시적으로 복사하고, 같은 가사·길이·BPM·조성·seed의 실제 Music 3 후보를 각각 한 번
  새로 만든다. 기준 파형은 모델 conditioning에 쓰지 않는다. 원본·정리본·실패·ASR 경고를
  보존하고 음악 기준 판정은 직접 듣기 전까지 `pending_human_listening`이다.

기준 곡 해시: `0f0087d86ed3f22209a67b77673cdb26b9cb41a5e9fd884bd64c91183d27ae9f`.

이번에 완료한 실제 새 생성은 다섯 번이다. 영어 원문 8줄·84 BPM·A minor·seed 202610071을

사용자는 `native60.wav`의 완성도가 많이 올라갔다고 느끼면서도 도입이 약하고 후렴 선율·

`enhanced60.wav`는 아직 `unreviewed`이며 기준 곡 이상의 음악성은 승인하거나 확정하지 않았다.
사용자의 마무리 요청에 따라 추가 추론은 진행하지 않았다.

보고서는 `.runtime/music3-quality-benchmark-20261005-01/report.json`, 같은 폴더의
`native60-report.json`·`enhanced60-report.json`, `.runtime/music3-quality-benchmark-20261005-02/report.json`이다.
두 프로젝트에 기준 후보를 재생용으로 명시적으로 가져왔고, 완료 artifact의 크기·SHA-256과

음향 합성의 정밀도를 비교하기 위한 BF16 depth/DiT 자산도 별도 ignored 폴더에 준비했다.
CPU 다운로드·shape/dtype·유한값·SHA-256 검증만 수행했다. 모델 로드·실제 추론·음악 A/B는
진행하지 않았고 기본 엔진이나 실행 설정에 적용하지 않았다. 예상 메모리나 개선 효과를
실측한 것처럼 취급하지 않는다.

최종 검사: Python **441개**, 앱 **97개**, Python 3.12.12 환경 동기화·문법·타입·빌드·diff 검사가
통과했다. 실제 음악 생성과 모의 계약 검사는 별도로 기록했다.

## 2026-10-05 Music 3 기본 엔진 전환

사용자가 MiniMax Music 3로 완전한 전환을 요청했다. 기본 Python/CLI 생성, 앱의 실행 관리와
설정·초안·피드백은 Music 3로 옮겼다. 과거 ACE 환경·모델·음원·요청·사람 평가·선택 이력은
삭제하거나 다시 쓰지 않는다. 과거 engine 없는 요청도 ACE로 판별하고 명시적인 legacy 선택
없이 새 엔진으로 재개하지 않는다.

- 모델: `mlx-community/MiniMax-Music3-mxfp8`, revision
  `d00a12c3c7f80eb66379dd02dd0f30ed0ce2d96e`.
- 구현: `mlx-audio` 0.4.8, upstream commit
  `784b29e2691a93ca7483147d86f61859dfaa6296`, MLX 0.31.2, Python 3.12.12.
- 추론 환경: `.runtime/minimax-music3/.venv`. 모델은 약 13GB이며 `.runtime/models/`에만 둔다.
- 기본 주소: `127.0.0.1:18002`. 인증 키는 private 0600 파일 `.runtime/music3-api-key`다.
- 생성은 text2music, 30 steps, 한 요청당 한 곡, 최대 요청 300초다. 실제 EOS 길이를 기록하며
  무음 padding으로 목표 길이를 위장하지 않는다. 커뮤니티 포트의 출력은 44.1kHz stereo PCM이다.
- Music 3 공개 포트의 미지원 cover·repaint·파형 참조는 앱과 CLI에서 차단한다. 특정 버전으로
  새로 만들기는 가사·편곡·제작 규칙으로 **새 전체 곡**을 만드는 동작이다.
- 설정은 schemaVersion 2로 옮기고 최초 원본을 `settings-before-music3.json`에 보존한다.
  기존 저장 위치·도우미·내보내기 위치·생성 기본값은 유지한다(길이 상한만 300초). 새 설치는
  60초·버전 하나가 기본이다. 앱에서 같은 Music 3만 준비된 엔진으로 인정하고 외부 서버는
  임의로 종료하지 않는다.
- 제작 규칙을 구조화 caption으로 매핑하고, inline·연속·사용자 정의 구간 태그 뒤 가사를 독립
  줄로 분리한다. 고정 upstream의 tag-led-line 정규화가 실제 가사를 버리는 문제를 막는다.
  실제 준비본·변경 사항·표현 지시는 새 요청에 남긴다. 과거 snapshot은 바꾸지 않는다.
- 초기 caption v2는 선택한 구간 전개 계획의 예상 시간·마디·구간별 강약을 caption에 전달했다. 모든 작성된 구절과
  후렴이 끝나도록 안내하고, 시간이 빠듯하면 간주를 줄인다. 시간표는 모델에 주는 안내이며
  실제 음원의 엄격한 시간 정렬을 보장하지 않는다.
- timeout 뒤 추가 seed 제출을 중단하고 미제출 seed를 기록한다. 취소는 로컬 작업 취소이며
  이미 제출한 원격 추론은 계속 계산할 수 있다.
- runtime owner 잠금을 작업 기록 읽기·복구보다 먼저 획득해 중복 프로세스가 진행 기록을
  변경하지 못하게 한다. 앱의 주소 변경과 도우미 메모리 인계도 소유 주소와 공유 잠금으로
  보호한다.

독립 검토에서 발견한 inline 가사 유실, 중복 runtime의 레지스트리 충돌, timeout 이후 추가
제출, 실행 중 주소 변경의 소유권 문제를 수정하고 회귀 검사했다. 원본·가사 순서·artifact
존재·크기·SHA-256·사람 `unreviewed`·요청 판본을 보존하는 계약은 그대로 유지한다.

실제 첫 검사는 영어 30초 요청에서 26.42초 음원이 나왔고 가사 순서 일치율은 94.6%였다.
최대 Metal 메모리는 28.31GB였다. 다음 한국어 생성 중 서버가 사라졌으나 로그와 종료 상태를
복구하지 못해 OOM과 실행 세션 수명 중 원인을 확정하지 않았다. 이 초기 부분 실패는
`.runtime/music3-transition-real-20261005-01/report.json`와 `exit-audit.json`으로 보존한다.

AR 프레임과 KV cache·음향 chunk를 즉시 평가하고, 생성 지역 변수가 해제된 뒤 cache를 정리하는
wrapper를 추가했다. upstream checkout은 수정하지 않았다. seed·sampling·CFG·overlap·crop
알고리즘은 유지하며 계산 결과의 bitwise 동등성까지 실증한 것은 아니다. 메모리 한도와 실제
active/cache/peak·RSS 관측을 health와 완료 metadata에 기록한다.

루트가 소유한 보완 서버에서 영어 30초·한국어 30초·영어 60초 **새 추론 세 번을 연속 완료**했다.
Metal peak는 각각 18.52GB·17.38GB·17.30GB였고 완료 후 active는 13.86GB로 돌아왔다.
모든 결과의 원문·요청·원본·정리본·WAV·검증된 명시 재개를 확인했다. 각 조건은 실제 한 번만
추론했으며 자동 재시도·과거 결과 재사용·사람 청취 승인은 없다.

| 영어 30초 | 30.02초 | 243.95초 | 24.3% | 도입이 길어 후렴을 전달하지 못한 후보, 경고 유지 |
| 한국어 30초 | 28.19초 | 255.56초 | 95.8%, CER 0.0417 | 구절·후렴 인식, 요청 길이 차이 경고 유지 |
| 영어 60초 | 60.07초 | 533.78초 | 76.3% | 새 2절은 전부 인식했으나 마지막 후렴 누락, 경고 유지 |

보고서는 `.runtime/music3-transition-real-20261005-02/report.json`이다. 같은 seed라도 첫 영어
검사와 후속 검사에는 caption 차이가 있으므로 가사 결과 차이를 메모리 수정의 효과로 단정하지
않는다. 실제 결과의 경고를 숨기거나 최신·대규모 모델이라는 이유로 음악적 우위를 확정하지 않는다.

새 2절 이후 후렴이 시간 예산에서 잘리는 현상을 보고, 구간 계획의 예상 시간·마디를 caption에
직접 반영하는 보완을 했다. 같은 가사·seed·모델·길이·sampling으로 별도의 새 영어 60초를
실제 생성했다. 60.07초 음원, 총 496.82초, 최대 Metal 17.30GB였으며 가사 일치율은 44.7%로
새 2절·마지막 후렴을 확인하지 못했다. 이 단일 seed 실험은 개선을 입증하지 못했다. 해당 경고를
유지하며 기본 추천 여섯 규칙을 더 늘리지 않는다. 추가 전개 계획은 선택형 안내다.
보고서는 `.runtime/music3-transition-real-20261005-03/report.json`, 통제 조건과 관찰은
같은 폴더의 `caption-comparison.json`에 보존한다.

격리된 Electron에서 기존 ACE 설정의 Music 3 마이그레이션·최초 백업·선호 보존·300초 상한,
새 설정 화면과 기존 음원 작업실·재생 파형·내보내기·미지원 수정 제거를 확인했다. 화면과 설정
검증 기록은 `.runtime/music3-transition-ui-20261005/`다. 실제 모델을 올린 앱 엔진 관리자에서도
외부 서버는 그대로 두고 도우미·주소 변경을 차단하는지, 앱 소유 서버는 준비 뒤 종료되어
offline이 되는지 확인했다(`lifecycle-external.json`, `lifecycle-owned.json`). 생성은 제출하지 않았다.

최종 Python 401개·앱 86개 검사와 환경 동기화·문법·타입·빌드·diff 검사가 통과했다. 초기 영어
한 번, 보완 후 연속 세 번, 입력 보완 한 번으로 **실제 성공 생성은 총 다섯 번**이다. 초기의
한국어 중단과 영어 미제출은 성공 횟수에 포함하지 않는다. 모든 완료 artifact의 SHA-256·크기와
사용자가 좋다고 한 기존 ACE 30초 원본의 해시를 확인했다. 새 결과는 전부 `unreviewed`다.

생성 중 즉시 평가 저장, 최초 입력 고정, 특정 작업 재개, SIGKILL 복구, 부모 버전 기반 수정,
불변 export, 구간을 바로 듣는 QC를 추가했다. Python 62개·앱 9개 회귀 테스트와 실제 ACE
30초 × 2, 120초 × 4, repaint, Electron 복구·동시 메모 저장을 확인했다.
변경 계약·재현 명령·실측 수치는 [검증 기록](VALIDATION-ASTRA.md)에 있다.

## 이번 실측 (2026-09-22, 실제 ACE 서버·실제 Ollama)

앱을 원격 디버깅 포트로 띄워 DOM 클릭과 실제 포인터 드래그로 조작했다. 임시 앱 데이터와 임시 곡
폴더를 써서 사용자 설정은 건드리지 않았다.

| 단계 | 결과 |
| --- | --- |
| 앱 시작 → ACE 자동 시작 | 모델 준비까지 32–42초 |
| 한국어 설명 → qwen3.6:27b 초안 | 24–40초, 제목·태그·한글 가사 |
| 30초 버전 2개 | 36–54초 |
| 자유 문장 피드백 → LLM 수정안 | 22초 |
| 6.6초 구간 repaint | 28–36초, 수정본 자동으로 열림 |
| 원본↔수정본 전환 | 재생 위치 유지하며 계속 재생 |
| export + inspect | 해시 일치, `restorable: true` |
| ⌘Q / SIGTERM | 앱이 켠 ACE가 2초 안에 종료 |

청취 판단(발음·음악성·연결부)은 아직 사람이 하지 않았다. 위 결과는 동작 검증일 뿐 품질 판정이
아니다.

## 실행

```bash
./app.sh          # 처음이면 환경 준비 후 앱 실행. 앱이 ACE 서버를 켠다
```

ACE 런타임이 없으면 먼저 `./scripts/bootstrap_ace.sh`. 로컬 LLM 도우미는 앱의 설정 → AI 도우미에서
Ollama와 모델을 고른다.

## 남은 작업

1. 사람이 p0와 새 곡의 버전·수정본을 듣고 발음·음악성·연결부를 평가한다. 특히 캡션+강도 방식의
   repaint가 예전 `instruction` 방식보다 나은지 같은 구간으로 비교한다.
2. 2분 곡 4 seeds 생성은 179.39초에 성공했다. 장곡 구조의 청취 평가, 메모리 정량 측정,
   LLM 도우미와 ACE를 함께 쓸 때의 여유 측정이 남았다.
3. 분리기·한국어 ASR을 채택해 가사 의심 구간을 수정안 입력(범위)으로 연결한다.
4. 청취 평가가 쌓이면 규칙 사전과 LLM 프롬프트를 실제 좋아요/별로 기록으로 조정한다.
5. 앱이 비정상 종료되면 앱이 켠 ACE 서버가 남을 수 있다. 다음 실행은 그 서버를 외부 소유로 쓰며
   앱에서 끌 수 없다.

# 자동 품질 검사

곡을 만들면 엔진이 가사 준비·검사·필요한 재시도·추천·재생본 정리·가사 누락 구간 수리를 수행한다. 판단 범위는
**파일·소리의 측정값과 받아쓴 가사의 일치**다. 멜로디·감정·음악적 취향의 평점이 아니며 모든 새 후보의 사람 청취 상태는
`unreviewed`다. 사람 청취와의 구분은 [청취 계약](QUALITY.md)에 있다.

## 기본 흐름

1. 원문과 목표 길이를 보존하고 모델에 보낼 준비본을 만든다.
2. 곡 하나를 생성하고 내려받은 원본을 파일·크기·SHA-256·PCM 기준으로 검사한다.
3. 음량·리듬·프레임별 스펙트럼 측정, 보컬 활동 추정, 원 믹스 받아쓰기와 가사 비교를 수행한다.
4. 재생성 근거가 있으면 같은 준비본에 새 seed를 쓴다. 버전마다 **첫 생성 1회 + 재시도 최대 3회**다.
   근거가 없으면 그 시점에서 끝내며, 검사가 불확실하다는 것은 근거가 아니다. 이 재시도는 다른 곡을 한 번 더
   뽑는 것이며 같은 곡을 고치는 것이 아니다. 같은 곡의 한 부분을 고치는 길은 [구간 수정](#구간-수정)이다.
5. 시도들을 아래 순서로 견주어 하나를 고르고, 원본을 보존한 정리본을 새 artifact로 만든다. 정리본마다
   [마스터링한 듣기용 사본](#듣기용-사본마스터링)을 따로 만들어, 앱은 그것을 재생하고 내보낸다.
6. 고른 곡에 부르지 않은 가사 줄이 확인되면 그 줄과 구간을 확인할 것에 올린다. `--repair-attempts`를 주면
   [그 구간만 다시 만들어](#가사-누락-구간-수리) 넣고, 고쳐진 것이 확인된 경우에만 그 결과를 추천한다.

추천 순서는 (1) 소리의 재생성 근거가 없는 것, (2) 가사가 통과한 것, (3) 남은 재생성 근거가 없는 것,
(4) 확인할 것의 수가 적은 것, (5) 가사 순서 일치 비율, (6) 소리 검사 점수다. 가사를 읽지 못한 시도는 읽어서
통과한 시도보다 뒤, 크게 틀렸다고 측정된 시도보다 앞이다. 이 순서는 한 요청의 시도들을 정렬할 뿐이고 사람이
어느 것을 좋아할지 예측하지 않는다(네 테이크 실측에서 사람이 고른 것은 가사 일치가 가장 낮은 테이크였다).

두 버전을 요청하면 각각 최대 4회 예산을 가진다. 모든 시도의 가사·스타일·음악 설정·예상 seed를 시작할 때
고정하고 재개에도 같은 예산을 쓴다. 제출했다가 실패·중단된 시도도 예산에 포함한다. `resume`은 그 작업의
계보·요청 fingerprint·실제 파일 검증을 통과한 완료 결과만 재사용하고, 새 `generate`는 과거 결과를 가져오지
않는다. 자동 추천은 사람이 고른 최종본과 평가를 바꾸지 않는다. 원본과 다른 시도는 화면의 자동 생성 이력에 남는다.

## 화면에 보이는 것

앱은 버전마다 **확인할 것**의 개수만 표시하고, 검사 탭 맨 위에 그 항목을 시각·듣기 버튼과 함께 보여 준다. 듣기를
누르면 그 구간이 선택되어 바로 구간 다시 만들기로 이어진다. 세는 것은 두 가지다.

- 이 버전에 남은 재시도 근거(없으면 가사 차이 경고), 재생본 정리를 마치지 못한 경우
- 관측이 아닌 경고: 들리지 않은 가사 줄, 박자 불안정·타격 시각 흔들림·반주 끊김·전체 신호 끊김 의심,
  무음·최대 음량 구간, 소리 찌그러짐 의심, 요청한 템포·조성 미반영 등

구간이 바뀔 때 생기는 음량·소리 색 변화(`loudness_shift`, `spectral_shift`)와 박자 단위 해석 차이
(`tempo_ambiguity`)는 구간이 있는 곡이면 늘 나오는 관측이라 세지 않고, 다른 측정값과 함께 '측정값 자세히'에 접어
둔다. 저장되는 `quality.status`와 CLI의 `status` 출력은 이 관측까지 포함한 묶음 상태여서, 확인할 것이 없는
버전도 `attention`일 수 있다.

## 가사와 곡 길이 준비

Unicode와 개행을 정리하고 100자를 넘는 줄은 기존 단어·문장부호 경계에서 나눈다. 단어와 순서는 바꾸지 않는다.
보컬곡에 끝 태그(`[Outro]`·`[Ending]`·`[End]`)가 없고 길이에 여유가 있으면 `[Outro]`를 더한다. 루프·갑작스러운
끝을 명시한 요청에는 더하지 않는다. 그 의도는 **사용자가 직접 쓴 스타일**에서만 읽는다. 프리셋·제작 규칙이
붙이는 문구(기본 규칙의 `repeating chord loop`)와 `piano loop` 같은 악기 반복 표현은 루프 음원 요청이 아니다.

가사 밀도는 음절 수와, 전체 길이의 75%를 보컬에 쓴다는 가정으로 추정한다. 초당 4음절 초과는 검토, 6음절
초과는 높은 밀도로 기록한다. 높은 밀도이고 랩·빠른 발화·루프·hard cut 의도가 없으면 초당 6음절에 맞춰 5초
단위로 길이를 늘린다(상한 ACE 600초, Music 3 300초. CLI·앱이 처음 요청할 수 있는 길이는 300초까지). 원래 목표
길이는 프로젝트 입력에 남고 적용한 길이는 요청에 고정되며 화면에 표시한다. 음원을 단어·문장 단위로 자르거나
숨·무음을 넣지 않는다.

## 소리와 가사 검사

PCM 검사는 전체 무음, 잘린 파형 꼭대기, 길이 차이, 채널별 DC offset, 파일 경계 진폭, stereo의 mono 상쇄,
RMS/peak를 기록한다. 재생성 근거는 전체에 가까운 디지털 무음, 클리핑, 큰 길이 차이뿐이다. 나머지는 청취
경고다. FFmpeg로 integrated LUFS·LRA·true peak를 측정만 한다.

클리핑은 **그 파일 자신의 peak**에서 잰다. ACE는 출력을 −1 dBFS로 맞추므로 잘린 파형도 full scale에 닿지
않는다. peak의 99.9% 이상에 같은 극성으로 3샘플 이상 머문 샘플의 비율(잘린 꼭대기)과, 그 띠의 샘플 수를 바로
아래 같은 폭의 띠와 견준 비율(8배 이상이면 잘린 것, 매끄러운 큰 소리는 2–3배)을 함께 본다. 잘린 꼭대기가
0.1% 이상이면 재생성 근거(`sustained_clipping`), 0.01% 이상이면 청취 경고(`clipping_suspected`)다. 저장된 실제
생성 118개에서는 한 건도 해당하지 않았다. 부드럽게 눌린(soft clip·limiter) 왜곡은 이 검사로 찾지 못한다.

UMXHQ는 CPU에서 보컬 활동 구간·비율과 vocal/mix 에너지 비율을 추정한다. 분리 오차가 있으므로 이 값만으로
보컬이 묻혔다거나 곡이 미완결이라고 판정하지 않는다. 분리한 보컬을 다시 섞거나 키우지 않는다.

Whisper에는 기대 가사를 주지 않는다. 원 믹스를 30초 창으로 받아쓰고(`condition_on_previous_text=False`)
segment의 timestamp·log probability·no-speech probability·compression ratio를 남긴다. 한글은 CER, 영어는 WER,
전체는 순서가 일치한 단위의 비율로 비교한다. 작성된 후렴 반복은 각각 따로 센다. `[Chorus x2]`는 반복으로,
`[Chorus 2]`는 구간 이름으로 읽는다. 신뢰도가 부족하거나 환각·과도한 반복으로 확정할 수 없으면 `unknown`이다.

전주 위에서 열린 30초 창은 "Oh, oh, …" 같은 지어낸 음절로 채워지고 뒤따르는 1절을 통째로 놓칠 수 있다.
그래서 두 가지를 한다.

- 첫 창은 UMXHQ가 1초 이상 이어지는 보컬을 처음 잡은 지점의 1초 앞에서 연다.
- 연달아 들리지 않은 가사 줄(줄마다 일치 20% 이하, 합쳐 6단위 이상)이 있으면, 그 줄이 있어야 할 구간(앞뒤로
  일치한 segment 사이)을 **다른 시작점 최대 세 곳**에서 다시 받아쓴다. 다시 읽은 결과는 작성한 가사와 더 많이
  일치할 때만 그 구간의 첫 결과를 대신한다. 가사를 본 적 없는 인식기가 우연히 더 일치할 수는 없기 때문이다.

다시 읽어도 나오지 않은 줄만 "가사 N줄이 들리지 않아요"(`lyric_lines_missing`)로, 첫 줄과 구간을 적어
확인할 것에 올린다. 다른 시작점의 재확인이 두 번에 못 미치면 확정하지 않은 `lyric_lines_unclear`다. 저장된
3분 곡 네 테이크로 실측하면, 불렀는데 0%로 기록됐던 1절 세 건이 92–96%로 읽혔고(전체 0.82–0.85 →
0.94–0.96), 두 테이크에서만 줄을 가리켰다: 보컬이 15초에 시작하는 테이크의 1절 첫 두 줄(0–18초)과 다른
테이크의 마지막 한 줄(177–180초). 저장된 다른 곡 16테이크에서는 확인된 누락 2, 확정 못 한 것 1, 받아쓰기를
믿을 수 없어 판단하지 않은 것 6, 이상 없음 7이었다. 다시 읽는 데 곡당 4–6초가 더 든다.

| 가사 재시도 기준(신뢰도 조건을 만족할 때만) | 최소 문맥 |
| --- | --- |
| 순서 일치 비율 0.65 미만 | 기대 단위 20개 이상 |
| 한국어 CER 0.65 초과 | 한글 20음절 이상 |
| 영어 WER 0.75 초과 | 영어 6단어 이상 |
| 작성된 후렴 일치 비율 0.5 미만 | 그 후렴의 기대 단위 8개 이상 |
| 작성된 구절 하나가 통째로 없음(일치 0.25 미만이고 모든 줄을 다시 읽어도 못 찾음) | 그 구절의 기대 단위 16개 이상, 다른 시작점의 재확인 2회 이상 |

그보다 짧은 누락(한두 줄, 한 줄짜리 Outro)은 다른 곡을 뽑을 근거가 아니다. 줄과 구간을 확인할 것에 올리고
[그 구간만 다시 만든다](#가사-누락-구간-수리).

임계값은 이 앱의 휴리스틱이며 발음의 정답 판정이 아니다. ASR 미설치·실패·낮은 신뢰도, 서버 불통·모델
불일치·추론 timeout은 다시 만들 이유가 아니다(timeout 뒤에도 서버 추론이 계속될 수 있다).

**알려진 한계**: 보컬 시작점은 분리 추정이라 전주의 보컬 비슷한 소리를 노래로 잡을 수 있다(네 테이크 중
둘). 그때는 위의 다시 읽기가 바로잡는다. 다시 읽기도 같은 Whisper이므로 독립된 두 번째 판정이 아니며, 가사를
또박또박 부르지 않은 줄을 없는 줄로 읽을 수 있다. 한 줄의 일부만 빠진 것, 줄 순서가 바뀐 것, 발음이 틀린
것은 줄 단위로 가리키지 않는다. 한국어 곡에서 이 줄 단위 판정을 실측한 기록은 아직 없다.

검사기 하나가 실패해도 나머지 근거는 남는다. 받아쓰기·박자 구간 진단이 실패하면 그 항목만 `unknown`이 되고
보고서의 `inspectionErrors`에 단계와 오류를 적으며, 이미 측정한 소리 결함(무음·클리핑·길이)과 그 재생성
근거는 그대로 쓴다.

## 리듬·프레임 검사

`--quality auto`와 `audio`는 결과 WAV를 모델 없이 분석하며 연주곡에도 적용한다. 요청에 고정한 BPM·박자표가
비교 기준이고, 적지 않았으면 정답을 채우지 않는다.

- 전곡 반복 박동 추정, 구간별 변화와 드리프트, 박자 후보 간격의 중앙값·MAD·95백분위 편차
- 요청 BPM과 추정 주기의 차이(절반·두 배·마디 단위로 읽는 경우 포함)
- 프레임별 RMS·peak, 스펙트럼 중심, 저·중·고역 비율, spectral flux(화면용은 최대 2,400개 지점으로 줄여 저장)
- 요청 박자표로 계산한 예상 마디 길이. 실제 다운비트를 검증한 값이 아니다

위의 전곡 박동 추정은 요청을 보지 않고 가장 빠른 강한 반복을 고르므로 박의 절반·두 배를 자주 고른다(저장된 곡에서
98 BPM 곡을 48, 125 BPM 곡을 250). 그래서 **실제 연주 템포**(`quality.playedTempo`, `played_tempo.py`)를 따로 잰다.
요청 BPM(없으면 엔진이 고른 BPM) ±12% 안에서 곡 전체의 타격 자기상관(1–4박)으로 박 주기를 찾고, 박마다 가장 가까운
타격에 직선을 맞춰 다듬는다. 박의 단위는 요청이 정하고 값은 측정이 정한다. 반복이 약하거나(대비 1.5 미만) 찾은 값이 범위
끝에 걸리면 템포를 적지 않고 `unknown`이다. 정리본도 자기 파일에서 다시 재며, 값은 그 파일의 SHA-256에 묶인다. 결함이
아니므로 확인할 것·재생성 근거가 되지 않는다. 저장된 ACE 테이크에서 84 BPM 요청은 84.0–87.6, 98은 88.2–96.8, 80은 88.3으로
연주됐고 116·125는 1.6% 안이었다. 이 측정 이전에 고정된 품질 계획은 재개해도 이 값을 만들지 않는다.
`analyze-rhythm --bpm`도 같은 값을 `playedTempo`로 낸다.

박자 검사(`beatTiming`)의 기준 주기는 바꾸지 않았다. 실제 연주 템포를 기준으로 쓰면 비교하는 구간은 늘지만, 사용자가
짚은 'city lights' 42초 박자 깨짐은 여전히 잡히지 않았고 사용자가 좋다고 한 'Night Bus'에 확인되지 않은 경고(54–58초)가
새로 생겼다.

템포 추정은 약한 드럼·당김음·half/double-time·의도된 템포 변화에 흔들린다. 음량·스펙트럼 변화는 후렴의
악기 추가나 브레이크일 수 있다. 그래서 리듬 경고는 **청취 확인용**(`retryEligible=false`)이고 재생성·시간
늘리기·퀀타이즈를 실행하지 않는다. 정리본은 다시 측정해 `measuredArtifactSha256`에 연결한다.

```bash
uv run music-engine analyze-rhythm path.wav --bpm 84 --time-signature 4/4   # 읽기 전용
```

## 엔진이 적용한 템포·조성·박자 확인

ACE는 실제로 조건으로 쓴 `bpm`·`keyscale`·`timesignature`를 결과와 함께 돌려준다. 요청한 값이 도중에 버려지면
text2music에서는 LM이 고른 값이, repaint·cover에서는 `N/A`가 돌아온다. 자동 검사는 요청에 적은 항목만 비교한다
(BPM은 정수로 반올림, 조성은 대소문자·공백 무시, `4/4`와 `4`는 같음). 다르면 `engine_meta_mismatch` 경고
(화면 "요청한 템포 미반영")와 `quality.engine`에 두 값을 남긴다. 같은 입력은 seed를 바꿔도 같은 값이 버려지므로
재생성 근거로 쓰지 않는다. 소리를 측정한 것이 아니라 엔진의 보고를 대조한 것이다. Music 3는 이 값을 보고하지
않아 비교하지 않는다.

## 박자·반주 구간 진단

새 품질 계획은 `diagnosticsVersion=rhythm-diagnostics-v4`를 고정한다. 네 항목을 따로 검사하고 근거가 부족하면
`unknown`으로 둔다. 과거 계획(v1–v3)은 재개해도 그때의 검사 범위를 유지하고 저장된 보고서는 다시 쓰지 않는다.

| 항목 | 보는 것 |
| --- | --- |
| `beatTiming` | 반복 박동이 충분히 관측된 구간에서 타격 간격의 편차와 구간별 변화. 빠진 박동은 타격 소리 쉼, 필인은 불확실성으로 둔다 |
| `backingContinuity` | 분리한 반주가 주변보다 급격히 줄었다 돌아오는데 보컬은 계속되는 0.2–4초 구간. 분리 근거가 없으면 판단하지 않는다 |
| `mixContinuity` | 곡 중간의 80 ms–4초 디지털 무음(모든 채널이 거의 0, 주변 대비 45 dB 이상 감소, 경계의 급격한 변화) |
| `hitTiming` | 같은 곡의 다른 반복과 비교해 타격이 연달아 빠르거나 늦은 구간. [타격 시각 검사](TIMBRE-TRACKING.md) |

모델 없는 타격 성분 추정(median HPSS)은 공격음과 지속음의 스펙트럼 근사이며 반주 끊김 판단에는 쓰지 않는다.
보컬·반주 근거는 UMXHQ의 250 ms 에너지 시계열을 원본 SHA-256에 연결해 쓴다. 선택적인 드럼 가중치
(`drums-9619578f.pth`, 35,637,796 bytes, SHA-256 `9619578f885c54737cb0234f9f9a4a679ee4f31438fd77fd1dbe02bb16c2da0a`)는
`quality_worker.py setup --drums`로만 받는다.

`analyze-rhythm --diagnostics`는 읽기 전용이다. `--separation-json`은 원본 해시와 시각별 mix 에너지가 실제 WAV와
맞을 때만 받는다. `inspect-rhythm`은 기존 후보에 새 보고서 artifact·job·revision을 더하고 기존 QC·음원·선택·
사람 평가를 덮지 않는다.

진단 범위 밖: 연주곡의 반주 누락, 4초보다 긴 끊김, 돌아오지 않는 소실, 음색·화성·멜로디 오류. 분리 오차·
스윙·필인·루바토는 원인으로 남는다.

### 구간별 의도 대조

프롬프트의 `rubato` 같은 단어만으로는 경고를 낮추지 않는다. 의도된 템포 변화나 쉼은 **검사할 음원의
SHA-256**에 연결한 계획으로 알린다.

```json
{
  "version": "rhythm-intent-v1",
  "sourceArtifactSha256": "검사할 WAV의 64자리 소문자 SHA-256",
  "sections": [
    {"startSeconds": 16, "endSeconds": 18, "name": "보컬만 남는 쉼", "expectedRest": true},
    {"startSeconds": 32, "endSeconds": 48, "timingIntent": "tempo_change"}
  ]
}
```

```bash
uv run music-engine analyze-rhythm path.wav --diagnostics --intent-json intent.json
uv run music-engine inspect-rhythm projects/my-song --candidate-id <candidate-id> --intent-json intent.json
```

- `expectedRest=true` 또는 `accompanimentExpected=false`: 측정한 반주 감소 구간 **전체**가 계획 안에 있을 때 편곡
  쉼 후보로 분류한다. 전체 신호의 디지털 무음은 `expectedRest=true`만 덮는다.
- `timingIntent`(`rubato`·`tempo_change`): 구간 전체가 계획에 포함된 템포 드리프트만 안내로 낮춘다. 계획 안의
  불규칙한 흔들림, 일부만 겹치는 계획은 경고로 남는다.
- 입력은 최대 64 KB·128개 구간이다. 저장 검사에는 정규화한 계획과 입력 파일 해시를 남겨, 나중에 파일을 바꿔도
  과거 검사의 의미가 바뀌지 않는다. 분리 근거가 없으면 계획만으로 반주 검사를 통과시키지 않는다.

계획과 맞아도 사람 청취 승인은 아니다.

### 검증된 범위

실제 기존 음악 9곡에 통제된 변형을 넣어 평가했다(2026-10-09, 조정용 5곡 / 코드를 고정한 뒤 처음 평가한 4곡).

| 통제 변형 | 조정용 | 처음 평가 |
| --- | --- | --- |
| 50–130 ms 시간 교란을 `hitTiming`이 찾음(정답과 50% 이상 겹침) | 44/60 | 18–22/48 |
| 0.1–1.5초 전체 믹스 끊김을 `mixContinuity`가 찾음 | 15/20 | 7/16 |
| 부드러운 템포 변화·원곡·음량·페이드 파일에 경고 | 0/20 | 0/16 |

곡마다 0/12에서 11/12까지 갈렸다. 생성 모델이 실제로 내는 오류에 대한 사람의 구간 정답은 없어 자연 음악의
정확도는 측정하지 않았다. 평가 방법과 재현 명령은 [타격 시각 검사](TIMBRE-TRACKING.md#다시-평가하기)에 있다.

## 원본을 보존한 재생본 정리

`finished-audio`는 별도 파일·후보·request·`audio-finish` revision으로 저장하고 원본 SHA-256, 처리 내용, 전후
측정을 연결한다. 실패하면 검증된 원본을 추천하되 숨기지 않는다. 그 버전의 `quality.finishingError`와 화면의
확인할 것에 남기고, 작업은 `partial`로 끝나 '이어서 만들기'가 나온다. 이어 만들면 음원을 새로 만들거나 다시
검사하지 않고 정리만 다시 한다. 처리는 다음뿐이다.

- 채널 평균의 절대 DC offset이 0.002보다 크면 제거한다.
- peak 0.98과 true peak −1 dBTP 안에 들도록 선형 gain을 **낮춘다**. 올리지 않는다.
- 0이 아닌 급한 파일 경계에 최대 5 ms fade를 적용한다.

길이·sample rate·channel 수·PCM 폭을 유지한다. noise gate·EQ·compression·시간 늘리기·고정 LUFS 정규화는 하지
않는다. gain 감소는 이미 생긴 clipping을, fade는 끊긴 가사나 불완전한 끝을 복원하지 않는다. 정리본의 true peak를
다시 재서 −1 dBTP를 인증하는 단계는 없다.

## 듣기용 사본(마스터링)

엔진이 낸 음원은 마스터링 전 상태다. 'Night Bus'는 −13.8 LUFS, true peak와 음량 차이 11.8 dB, 좌우 상관 0.90(거의
모노)이었다. 같은 22초를 원본·마스터링·마스터링 + 16 kHz 위 재구성으로 만들어 모두 −14 LUFS(스트리밍 재생 음량)로
맞춰 들려주자 사용자는 마스터링한 둘이 "훨씬 깨끗하다"고 했고 둘의 차이는 듣지 못했다. 그래서 마스터링만 쓴다.

정리본(`finished-audio`)마다 `listening-copy` job이 `listening-audio` artifact를 만든다. 버전 자체는 바꾸지 않는다.
구간 수정은 버전의 원래 샘플을 다시 칠하고 이어 붙이므로, 마스터링을 버전에 넣으면 수정 밖이 두 번 마스터링된다.

- 처리: 25 Hz high-pass → glue compressor(−20 dBFS, 2.5:1, 20/200 ms) → 옆(side) +2.6 dB → drive → 4배 oversampling한
  limiter(−1.1 dBFS, look-ahead 지연 보정). FFmpeg 필터로 하며 `mastering`에 판본·필터 문자열·FFmpeg 판본·전후 측정을
  남긴다. sample rate에서 limiter를 돌리면 저장된 곡 73개 중 20개가 −1 dBTP를 넘었다(최대 +0.7).
- drive는 곡 전체가 −9 LUFS가 되도록 찾는다. 구간 수정본은 고친 버전의 drive를 그대로 써서 곡의 음량이 바뀌지 않는다.
- 측정(저장된 곡 23개의 버전 73개): 새로 찾은 drive의 53개는 모두 −9.0 LUFS, true peak는 모두 −1.0 dBTP 이하다. drive를
  물려받은 구간 수정본 20개는 −9.9 ~ −8.5 LUFS다. 길이·sample rate는 그대로이고 원본과 시간 어긋남은 0 샘플('Night Bus').
  구절과 후렴의 음량 차이는 유지됐다(구절이 0.8 → 1.0 dB 작음). 24-bit WAV로 쓰며 73개가 1.4 GB다.
- 3초보다 짧거나 소리가 없는 음원은 만들지 않는다. 실패해도 버전은 그대로이고 앱은 버전 음원을 재생한다.
  실패 이유는 그 `listening-copy` job에 남는다.
- 앱은 사본이 있으면 그것을 재생·파형 표시·Finder 보기에 쓴다. `export`는 사본을 쓰고, `--unmastered`면 버전 음원을 쓴다.
- `music-engine master <곡 폴더>`는 정리본이 대신한 원 테이크를 뺀, 앱이 재생할 수 있는 모든 버전에 사본을 만든다.
  마스터링 판본이 바뀌면 새 사본이 옛 사본을 대신하며, 옛 사본은 기록에 `retired`(대신한 사본)를 남기고 파일은
  기록된 SHA-256과 같을 때만 지운다. 사본은 버전에서 다시 만들 수 있으므로 버전마다 하나만 디스크에 둔다.
- 버전 음원은 지우지 않는다. 구간 수정·검사·다른 마스터링이 모두 그것에서 시작하고, 마스터링(압축·limiting)은
  되돌릴 수 없다.

ACE 음원에는 MP3 같은 대역 흔적이 남는다. 16 kHz 위가 거의 없고 16.5–18 kHz가 켜졌다 꺼지며(저장된 ACE 곡 5개에서
프레임의 6–24%), 하이햇 사이 6–16 kHz에 구멍이 생긴다. Music 3 곡에는 없었다. ACE는 디코더에서 WAV를 바로 쓰므로
모델 자체의 성질이다. 마스터링은 이것을 고치지 않는다(16 kHz 위 재구성은 사용자가 차이를 듣지 못해 버렸다).

## 가사 누락 구간 수리

전곡 재시도가 다른 곡을 뽑는 것과 달리, 이 단계는 **고른 곡 자체**를 고친다. 대상은 세 번 다시 받아써도
나오지 않은 가사 줄(`lyric_lines_missing`) 하나의 구간이다. **기본값은 꺼짐**이며 `--repair-attempts 1–3`으로
켠다. 첫 청취 비교에서 사용자는 두 곡 모두 보정 전을 더 낫거나 비슷하다고 했다. 전주 위에 새로 부른 두 줄은
불렸지만 그 선율이 곡과 어울리지 않았고, 다른 곡은 이음매에서 박자가 깨졌다(아래 템포 맞추기로 고친 문제).

1. **다시 만들 범위**: 그 줄이 있어야 할 구간(앞뒤로 불린 줄 사이) 안에서 보컬이 측정되지 않은 가장 긴
   부분이다. 그 부분이 4초 이상이고 빠진 줄을 초당 4음절 이하로 부를 수 있으면 다음에 불리는 줄의 0.25초
   앞까지를 쓰고, 아니면 구간 전체를 쓴다. 가사를 부를 자리가 없거나, 60초 또는 곡의 절반을 넘으면 고치지
   않고 확인할 것으로만 남긴다.
2. **시도**: [구간 수정](#구간-수정)으로 최대 세 번, 보통 → 많이 → 많이 강도로 다시 만든다. seed는 생성
   재시도처럼 batch를 만들 때 고정하고, 제출했다 실패한 시도도 예산에 포함한다.
3. **채택 조건(모두)**: 바뀐 구간 밖이 고치기 전과 샘플까지 같다. 같은 가사로 다시 받아썼을 때 일치한 단위가
   늘었다. 바뀐 구간에 들리지 않는 줄이 남지 않았다. 바뀐 구간과 그 앞뒤 1초, 또는 곡 전체에 대해 고치기 전에
   없던 확인할 것(박자·반주·소리)이 생기지 않았고 새 재생성 근거도 없다. 구간 밖은 같은 소리이므로 거기에 대한
   검사 결과는 비교하지 않는다.
4. 조건을 처음 만족한 시도가 그 버전의 추천본이 된다. 하나도 만족하지 못하면 고치기 전 곡을 그대로 추천하고
   들리지 않은 줄을 확인할 것에 남긴다. 버려진 시도와 고치기 전 곡은 자동 생성 이력에 남으며, 화면의 '비교
   버전'은 고치기 전 곡이다.

각 시도의 `quality.repair`에 대상 줄·범위·강도·채택 여부·버린 이유(`lines_still_unheard`·
`no_more_words_heard`·`new_place_to_check:<검사>`·`rest_of_song_not_preserved` 등)를 남긴다.
`--quality audio`와 커버·Music 3에는 적용하지 않는다. 채택 조건은 가사가 불렸는지와 측정값만 보므로, 새로 부른
선율이 곡과 어울리는지는 판단하지 못한다. 그것이 기본값을 끈 이유다.

**실측(실제 추론, 영어 3분 곡 두 곡)**

- 전주 뒤 1절 첫 두 줄을 부르지 않은 신스팝 곡: 같은 seed로 다시 만들어 전체 흐름을 돌렸다. 검사가 두 줄과
  0–18초를 가리켰고, 0–15초를 다시 만든 첫 시도(보통)는 여전히 부르지 않아 버려졌으며, 둘째 시도(많이)에서 두
  줄이 불려(1절 50% → 96%, 전체 0.91 → 0.96) 채택됐다. 15.01초 이후는 고치기 전과 샘플까지 같았다. 생성부터
  끝까지 372초였다. 따로 한 다섯 번의 수리 시도에서는 넷이 두 줄을 불렀고 하나는 한 줄만 불러 검사에 걸렸으며,
  넷 중 둘은 새 박자·반주 경고가 생겨 버려질 시도였다.
- 곡 중간(2절) 다섯 줄을 부르지 않은 감성 힙합 곡: 쉬는 부분이 없어 앞뒤 불린 줄 사이 29.8–63.2초 전체가
  범위였다. 세 시도 가운데 둘이 다섯 줄을 모두 불렀고(2절 100%, 전체 0.82 → 0.96) 하나는 세 줄이 남아 검사에
  걸렸다. 모두 불린 둘 중 하나는 바뀐 구간 안에 반주 끊김 의심이 새로 생겼다. 세 시도 모두 구간 밖은 고치기
  전과 샘플까지 같았다. 이 곡은 수리 방법만 실측했고 생성부터의 전체 흐름으로 돌린 것은 아니다.

**한국어 가사, 곡 끝의 누락, 세 번째 곡 이후에서는 아직 실측하지 않았다.** 채택은 받아쓰기와 측정으로 정하며,
고쳐진 구간이 듣기에 더 좋은지는 판단하지 않는다.

## 구간 수정

구간 수정(`repaint`)은 같은 곡의 한 부분만 다시 만든다. 엔진은 고른 구간을 새로 만든 뒤 나머지에 원곡 파형을
도로 붙이고 **전곡을 다시 peak에 맞춘다**. 그래서 엔진의 결과는 구간 밖 전체가 한 번 고칠 때마다 작아진다
(저장된 실제 수정 12건에서 0.8–1.0 dB). 앱은 내려받은 결과를 기록하기 전에 이렇게 바로잡는다
(`edit_splice.py`).

1. 수정 구간에서 3초 이상 떨어진 곳에서 엔진 결과와 원곡 사이의 gain 하나를 구한다. 그 gain을 되돌린 뒤에도
   차이가 −40 dB보다 크면(엔진이 원곡을 그대로 붙이지 않았으면) 엔진 결과를 손대지 않고 쓴다.
2. gain을 되돌린 결과와 원곡이 실제로 다른 곳을 10 ms 창으로 찾는다. 고른 범위에서 바깥으로, 100 ms 동안
   같아질 때까지가 바뀐 구간이다(실측: 고른 범위 ±10–30 ms).
3. 바뀐 구간 밖은 **원곡의 샘플을 그대로** 쓴다. 안쪽은 엔진이 준 소리를 원곡 기준 크기로 되돌려 넣는다.
   새 구간의 peak가 원곡 전체의 peak보다 높으면 그 꼭대기만 앞뒤 2.5 ms의 gain 곡선으로 낮춘다(실측: 최대
   1.0 dB, 구간당 14–104 ms, 구간의 RMS 변화 0.05 dB 이하). 2 dB보다 더 낮춰야 하면 엔진 결과를 그대로 쓴다.

**템포 맞추기**: 곡이 요청한 BPM과 다르게 연주되면(실측 예: 84 BPM 요청에 87.6) 요청값으로 다시 만든 구간은
요청 템포를 지키고, 끝 이음매에서 원곡의 박과 어긋난다. 그래서 수정 구간 앞뒤 최대 20초씩(구간 안은 제외)의
타격을 읽어 실제 템포를 재고, 요청과 1.5% 이상 다르면 그 템포를 반올림한 정수 BPM으로 요청한다. 요청
기록에는 `playedTempo`(요청·실측·사용 여부)가 남는다. 사용자가 63초 이음매에서 박자가 깨진다고 짚은 수정
(29.8–63.2초)을 같은 seed로 다시 만들어 비교하면, 84 BPM 요청에서는 구간 안이 84.4–84.6 BPM으로 연주되어 이음매의
박이 원곡 격자에서 68–125 ms 벗어났고, 88 BPM 요청에서는 구간 안이 87.4–87.7 BPM, 이음매 차이가 4–25 ms였다.
사용자는 88 BPM 쪽에서 박자가 깨지지 않는다고 확인했다. 정수 BPM만 보낼 수 있어 긴 구간에서는 소수점 이하
차이가 쌓일 수 있다. 저장된 곡 24개 가운데 20개가 요청 BPM과 1.5% 넘게 다르게 연주됐으므로(84 → 85.8–87.7,
98 → 88.5, 80 → 88.3, 96 → 89.6), 이 보정은 대부분의 수정에 적용된다. 버전에 기록된 곡 전체의 실제 연주
템포(`quality.playedTempo`)가 아니라 이음매 근처를 다시 재는 것은, 귀로 확인한 것이 이 방식이고 이음매에서 맞아야 할
것이 그 근처의 박이기 때문이다.

결과의 artifact에는 `splice`(적용 여부, gain, 실제 바뀐 구간, 꼭대기를 낮춘 양, 엔진이 준 파일의 SHA-256)가
남고, 화면의 자동 검사 탭은 "N–M초만 새로 만든 소리예요"라고 알린다. 적용하지 못한 경우는 이유
(`format_differs_from_source`·`no_stretch_far_from_the_edit`·`source_not_preserved_by_engine`·
`edit_much_louder_than_the_source` 등)와 함께 엔진 결과가 그대로라고 알린다. 곡 대부분을 고르면(양쪽 합쳐
1초 미만만 남으면) 적용하지 못한다.

`repaint`도 기본 `--quality auto`이며 수정 WAV 전체를 **한 번** 검사하고 정리본을 만든다. 이어 붙인 수정본의
정리본은 음량을 다시 낮추지 않는다(고친 버전의 크기를 따른다). 그래서 정리본도 바뀐 구간 밖이 부모 버전과
같다. 부모 버전의 고정된 가사·길이·음악 설정을 그대로 쓰고, 새 곡의 가사 준비·Outro 추가·길이 조정은
적용하지 않는다. 사용자가 요청한 구간 수정은 경고가 있어도 자동으로 다시 만들지 않는다. 원곡 → 수정 원본 →
정리본 계보와 `editRange`를 보존한다. 경계의 샘플은 이어지지만 박자·음색·가수가 자연스럽게 이어지는지는 검사하지 않으므로
직접 비교해 듣는다.

## 실행 환경과 중단 처리

`--quality audio`는 가사 모델 없이 음원 검사·정리만 하고, `--quality off`는 생성과 WAV 무결성 검사만 한다.
연주곡 `[Instrumental]`은 가사 모델을 올리지 않는다.

```bash
./scripts/bootstrap_quality.sh        # 가사가 있는 곡의 첫 검사 때 자동 실행된다
uv run music-engine generate projects/my-song --seeds 101 --quality-attempts 2
uv run music-engine generate projects/my-song --quality audio
uv run music-engine generate projects/my-song --repair-attempts 2   # 가사 누락 구간 수리 켜기
```

Apple Silicon macOS·FFmpeg·uv가 필요하다. 검사 환경 `.runtime/quality/.venv`(Python 3.12.12)는 프로젝트·엔진
환경과 분리되고, 패키지는 `requirements-quality.txt`와 `scripts/quality-requirements.txt`에 버전·해시로 고정한다.
준비됐다는 표시(`ready.json`)는 사용 가능하다고 적혀 있고 지금의 검사기 판·패키지 고정 파일과 맞을 때만
믿는다. 맞지 않거나, 분석 중에 가중치가 없거나 손상된 것이 드러나면 준비를 한 번 다시 실행한다.
가중치(약 1.65GB)는 `.runtime/models/quality`에 두며 Whisper revision과 모든 가중치의 SHA-256을 고정한다. 분석은
offline이고 음원·가사를 네트워크로 보내지 않는다. 모델·라이선스는 [결정 기록](DECISIONS.md)에 있다.

bootstrap과 무거운 분석은 파일 잠금으로 직렬화하고, 분석이 끝나면 worker가 종료해 메모리를 반환한다. 호출한
CLI가 사라지면 250 ms 간격의 watchdog이 worker와 bootstrap 자식 프로세스를 멈춘다.

## 실제 추론으로 확인하기

모델 없는 회귀 검사는 실제 추론 검사를 대체하지 않는다. 생성과 검사 전체는 켜 둔 XL turbo 서버에서 새
30초 연주곡을 한 번 만들어 확인한다. 원본·정리본의 분석 해시와 `unreviewed` 상태를 검사한다.

```bash
./scripts/start_ace_api.sh
# 다른 터미널에서, 존재하지 않는 출력 디렉터리를 지정한다.
uv run python scripts/smoke_rhythm_quality.py --output-dir .runtime/rhythm-smoke-new
```

손으로 켠 서버는 저절로 꺼지지 않으니 검사가 끝나면 끈다.

## 자동 검사가 하지 않는 것

멜로디·화성·실제 박자표·마디 강세·가수 음색의 일관성, 감정 표현, 자연스러운 발음, 구간 수정 경계의 음악적
연결, 곡이 자연스럽게 끝났는지는 판단하지 않는다. 자동 보컬 재믹스, 강제 음절 절단, 주관적인 장르 점수,
가사 누락 밖의 결함(박자·반주 끊김·끝 잘림)을 자동으로 고치는 처리는 구현하지 않았다
([남은 보정 설계](ONE-SONG-FINISHING-DESIGN.md)). ACE의 DiT Lyrics Alignment
Score는 고정한 v0.1.8 REST/MLX 경로에서 받을 수 없어 쓰지 않는다. Whisper는 speech ASR이어서 노래에서는
신뢰도가 높아도 가사를 잘못 읽을 수 있다.
